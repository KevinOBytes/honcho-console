# Testing

Honcho Console uses a small layered validation set:

- `npm run lint` — Next/React lint rules, including hook and accessibility checks.
- `npm run typecheck` — TypeScript project diagnostics.
- `npm test` — Vitest unit tests for configuration normalization, resource-ID validation, authenticated client requests, replacement sequencing, formatting helpers, the change journal, memory composition aggregation, export builders, feature client methods (chat, representation, searches, summaries, dreams, queue), and every API route including the journal-recording mutations, bulk deletion (confirmation, bounds, partial failure), id collection for select-all-matching, session and webhook deletion, and the multi-select UI (header checkbox, typed confirmation, filter persistence after delete, peer purge).
- `npm run build` — production Next.js compilation and route generation.
- `npm run project-check` — repository-contract validation.
- `npm run smoke` — read-only live smoke against the running local app; set `HONCHO_UI_URL` and `HONCHO_UI_WORKSPACE` when needed. It checks status/default workspace selection, overview resources, memories, peers, sessions, context, messages, response credential-marker absence, plus the feature additions: composition stats, change journal, queue status, session summaries, Markdown export size/header, labeled global message search, and a negative dream-validation probe (invalid `dream_type` must be rejected with 400 before any deriver work). It never mutates Honcho.

Browser QA must inspect the overview (composition bars, sparkline, recent changes, export), memory browser/editor (session filter, session links, original-versus-replacement preview), peer context (dialectic ask, representation inspector, dream confirmation gate, per-peer message search), session archive (summaries panel, cross-link focus), and global search at desktop and narrow widths. Exercise bulk deletion only on temporary, clearly marked conclusions and an empty temporary session, then confirm none remain; open the peer purge and webhook dialogs against real data only to inspect them and cancel. Confirm keyboard names/focus states, no console errors, responsive overflow behavior, and explicit confirmation before destructive memory/card actions and dream scheduling. A real dialectic/representation round-trip at the minimal reasoning level is acceptable during QA; real dream scheduling is not (it triggers deriver work — verify the confirmation gate and request body only).
